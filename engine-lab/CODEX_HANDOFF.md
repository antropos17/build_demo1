## Что пользователь строит

Руслан делает механический 2D sandbox: двигатель в разрезе на испытательном стенде, видимые поршни, износ, трещины, масло, охлаждайка, выхлоп, звук, внутренняя физика осколков. Он ожидает применённые изменения и запускаемую сборку, не очередной план или патч для ручной вставки.

Последние приоритеты: улучшить весь существующий проект, детализацию и реализм; использовать настоящие доступные записи звука, а не синтетический двигатель; скачивать проверяемые ассеты или делать собственные SVG. Дым должен быть выразительным, но не скрывать разрез. Осколки должны биться и застревать внутри механизма, влиять на него, а не только вылетать наружу. Работа должна оставаться плавной.

Отвечай пользователю по-русски, коротко, с конкретными изменениями и проверкой. Не объявляй физику инженерно точной. Не заявляй, что звук прослушан, сайт опубликован или проверки пройдены без фактического выполнения.

## Неприкосновенные правила

1. **Последний цилиндр не погибает.** Допускается 4 → 3 → 2 → 1, но не Game Over, автоматический сброс или терминальный отказ. Остановить мотор можно вручную ключом. Поддержка последнего цилиндра намеренно игровая.
2. Охлаждение, остановка, подзарядка АКБ и перезагрузка страницы не ремонтируют мотор и не возвращают потерянные цилиндры. Полный сброс только вручную с подтверждением.
3. Газ и тормоз независимы, аналоговые и мгновенно отпускаются при отмене ввода. Два пальца и несколько клавиш не должны конфликтовать. Тормоз нагружает вал стенда, это не автомобильная скорость в км/ч.
4. Сохранять состояние повреждений, жидкостей и внутренних осколков. Не сохранять нажатые педали или активный стартер. Текущая версия сохранения: **7**; необходима миграция при её изменении.
5. Настоящие WAV и их лицензии сохранять. Нельзя тихо вернуть синтетический основной двигатель или заменить записи тестовым тоном. Автономная HTML должна работать без сети.
6. Физика и случайность принадлежат модели. `render()` не меняет модель, время, износ, позиции осколков или RNG. Пауза осмотра должна действительно замораживать механизм.
7. Ограничивать частицы, осколки, аудиоголоса и кэши. Сохранять экономный режим, снижение тряски и корректную приостановку скрытой вкладки.
8. Не переписывать всё в React/Three.js и не удалять рабочие системы ради косметического упрощения без отдельного запроса.

## Запуск и проверка

Рабочий каталог для всех команд: **`engine-lab/`**, а не корень родительского репозитория.

```sh
npm run assets:verify
npm test
npm run build
```

Node.js >=20; при упаковке использовались Node 22.16.0 и npm 10.9.2. У проекта нет npm-зависимостей, `npm install` для этих команд не нужен. Открой `dist/last-piston.html`; нажми **ЗАПУСК**, затем педали. Нулевые обороты до включения ключа являются штатным состоянием.

Модульный вариант можно обслуживать обычным статическим сервером:

```sh
python -m http.server 8000 --bind 127.0.0.1
```

Актуальный браузерный набор, не старые `check_dashboard.py`/`check_ignition.py`:

```sh
python tools/check_assets.py
```

Ему нужны Python, Playwright и Chromium; путь к браузеру задаётся `CHROMIUM_PATH`. Установка тестовых инструментов может потребовать сеть, сама игра не требует её. Скрипт загружает автономную HTML, блокирует HTTP и проверяет настоящие встроенные WAV. Вывод: `dist/verification-13/`.

В браузере `?test` или `window.__PISTON_TEST__=true` перед загрузкой включает `window.__engineLab`. Доступны модель, renderer, audio, pause, advance, restore, stepInputs и reset. Для регрессионных тестов используй этот интерфейс; не включай его обычным игрокам автоматически.

## Карта кода и важный порядок загрузки

Приложение написано на JavaScript без фреймворка. Браузерные модули расширяют `window.Piston`, модель также экспортируется через CommonJS для Node. Порядок скриптов в `index.html` является частью архитектуры.

| Задача | Файлы |
| --- | --- |
| Базовое состояние, сохранения, кинематика | `src/simulation.js`, `src/dynamics.js` |
| 720°, клапаны, контактный износ | `src/mechanics.js` |
| Температуры, жидкости-резервуары, реле вентилятора, рейтинг | `src/powertrain.js` |
| Инерция вала, газ, тормоз, нагрев и fade стенда | `src/dyno.js` |
| Ключ, стартер, АКБ, генератор, выбег | `src/ignition.js` |
| Актуальная модель: внутренние осколки, контакты, зажатия, контуры жидкостей | `src/internals.js` |
| Базовая графика и накопленные слои разреза | `src/renderer.js`, `workshop.js`, `cutaway.js`, `effects.js`, `bench.js`, `realism-view.js` |
| Финальный renderer, SVG-кэш и осмотр деталей | `src/asset-renderer.js`, `assets/mechanical-atlas.js` |
| Источники, обработка PCM и действующий проигрыватель | `src/sample-bank.js`, `audio-utils.js`, `sample-audio.js`, `assets/soundbank.js` |
| Исторический DSP, не активный основной звук | `src/audio.js`, `src/mechanical-audio.js` |
| Ввод, приборная панель, зажигание, жизненный цикл | `src/pedals.js`, `dashboard.js`, `ignition-panel.js`, `app.js` |
| Разметка и накопленные стили | `index.html`, файлы CSS в корне проекта |
| Упаковка одной HTML | `tools/build.cjs` |

Итоговая модель импортируется в Node из `src/internals.js`. Не тестируй новые системы исключительно через устаревший базовый класс. Новые свойства нужно проверять на всей цепочке наследования и в `restore()`.

## Ассеты

Шесть исходных WAV лежат в `assets/audio/`; идентичные байты встроены в `assets/soundbank.js`. Восемь SVG лежат в `assets/svg/`, встроенный atlas: `assets/mechanical-atlas.js`. Происхождение и лицензии: `SOURCES.md`; хеши: `assets/audio-manifest.json`, `assets/svg-manifest.json`.

```sh
npm run assets:verify
npm run assets:svg
npm run audio:fetch
```

`assets:svg` заново создаёт SVG из `tools/make-svg-assets.py`. Правь генератор вместе с SVG, иначе правки будут потеряны при регенерации. `audio:fetch` нужен только для восстановления/обновления банка, обычному игроку он не нужен. Не заменяй проверенный банк, пока новые файлы целиком не скачаны, лицензия не проверена и тесты не пройдены.

Записи очень короткие и универсальные, не единый заводской набор конкретного I4. Пик/RMS и исправленный шов не гарантируют приятный тембр. Акустическую оценку нужно проводить прослушиванием, отдельно от автоматических тестов.

## Границы реализма и документационные долги

- Это продольная схематическая проекция с развёрнутыми узлами, а не CAD-копия конкретного двигателя.
- Контакты используют приближённые формы, жидкости представляют сеть малых объёмов. Это не деформируемые 3D-тела и не CFD.
- Визуальная частота вала замедлена для читаемости; звук следует рабочим оборотам. Не связывай их напрямую и не делай поршни невидимыми на 6500 RPM.
- Нормальный и стрессовый режимы различаются. Не переносить ускоренное старение в нормальную эксплуатацию.
- `ENGINEERING.md` содержит исторические строки о 10.5:1 и старом управлении RPM. Текущие `SPEC`/`RATING` используют **9.8:1**, актуальный вал интегрируется в `dyno.js`. Это долг документации, не повод откатывать код.
- Старые release-файлы и браузерные скрипты описывают свои версии. Основная актуальная проверка: `check_assets.py`.

## Следующая итерация в Codex

Сначала установи базу по текущим исходникам и выполни проверки. Затем продолжи последнюю задачу пользователя ограниченными, реально применёнными изменениями:

1. Прослушать имеющиеся реальные слои и улучшить переходы RPM/load, запуск и удары. Если заменять записи, брать совместимый лицензированный набор с происхождением и хешами. Не добавлять синтез вместо записи.
2. Углубить видимую физику контактов: клин в зазоре, трение о подвижную поверхность, отсутствие прохождения сквозь стенки и самопроизвольного освобождения. Проверять детерминизм, сохранение и последний цилиндр.
3. Уточнить трубопроводы и выпуск: читаемое направление потока, пузырьки и уровень по модели, пульсирующий выхлоп, утечки по повреждённым стыкам. Дым не должен закрывать весь механизм.
4. Увеличивать детализацию через кэшируемые векторные элементы и износ конкретной детали, а не декоративное свечение. До/после снять одинаковую повреждённую сцену и замерить стоимость кадра при фиксированных настройках.

Это очередь улучшений, не утверждение, что они уже реализованы или неисправны. Выбирай доказуемое улучшение после осмотра кода. Не начинать с новой системы коробки передач, автомобиля, аккаунтов или монетизации.

Готовая итерация: изменения в исходниках, регрессионные тесты, новая собранная HTML, краткий список применённых улучшений и честные результаты проверок. Не выдавать пользователю куски кода для вставки. Не переписывать историю и не делать force-push. Новую версию назначай только после фактических изменений игры.
